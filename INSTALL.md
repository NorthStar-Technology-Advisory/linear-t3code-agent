# Install the Linear ↔ T3Code bridge

This guide adapts the upstream service deliverable. Choose your own hosting and process supervisor. Provision a dedicated account for the bridge and T3Code with only intended repository credentials and integrations. Delegation grants full coding and draft-PR permissions; project labels and worktrees do not confine filesystem access.

1. Install Node.js 22.13 or newer, npm, git and GitHub CLI. Authenticate `gh` as the service account. Configure git commit identity. Clone intended repositories and verify the account can create worktrees and push branches.
2. Run T3Code on localhost or a private network. Configure its providers/models and create a T3Code project for each repository. Give each project a unique title and configure its model and workspace preference, or environment defaults. Obtain a server-side bearer credential permitting orchestration reads/commands, settings/provider reads and VCS branch/status reads using T3Code's current [environment authentication](https://github.com/pingdotgg/t3code/blob/main/docs/internals/environment-auth.md) flow. Store credentials only in the private service environment; do not put them in Linear issues or public URLs.
3. Clone this service separately from target application repositories. Run `npm ci`, copy `.env.example` to `.env`, and fill in the Linear credentials, T3Code connection and authentication. In Linear Settings → Projects → Labels, create one **T3Code project** group and select a child label on each Linear project whose name exactly matches an active T3Code project title. No UUID routes or bridge model defaults are required. The paths must refer to the same files for both processes. Use local durable storage for `BRIDGE_DB_PATH` and `WORKTREE_ROOT` (context and attachments). T3Code chooses worktree locations.
4. Create a Linear OAuth app, using your public HTTPS URL plus `/linear/oauth/callback` as the redirect URI and `/linear/webhook` as the webhook URL. Enable Agent Session events and Issue update events. The installation uses `read`, `write`, `app:assignable`, and `app:mentionable` scopes. Set the app's webhook secret in `LINEAR_WEBHOOK_SECRET`. Configure a random `INSTALL_SECRET` of at least 16 characters before exposing the install route.
5. Run `npm run typecheck` and `npm run build`, then `npm start`. Forward only the required bridge endpoints through your HTTPS proxy. Verify `/healthz`, then run `npm run smoke:webhook` to check signing and freshness. These checks do not start coding work.
6. Open `/linear/install?install_secret=...` privately and complete OAuth. Avoid retaining the secret-bearing URL in proxy logs. An Authorization Bearer header is also accepted by the install endpoint. The access and refresh tokens are stored in `TOKEN_STORE_PATH` with private permissions.
7. Install `grill-me`, `to-spec`, `to-tickets` and `implement` for the selected provider in the T3Code execution environment. Confirm workspace skill discovery. Configure team status descriptions with the exact `t3code: <skill>` markers described in [status-driven workflows](README.md#status-driven-workflows); leave review/holding statuses unmarked. The bridge does not distribute skills.
8. Exercise [NOR-197 live acceptance](docs/acceptance/nor-197.md): delegate into grilling, answer in Linear, have a human advance to spec and tickets, then delegate a child for implementation. Verify thread continuity, published artifacts, an active transition and restart.
9. Delegate a disposable representative issue in a labelled project. Verify its thread and configured workspace mode, draft PR and validation report. Send a follow-up and verify the same PR updates. Restart the bridge during work and verify recovery. Stop an active session from Linear and verify edits survive and queued prompts are cleared. Exercise a question and an explicit approval. Record results using [docs/acceptance/nor-173.md](docs/acceptance/nor-173.md) and [NOR-198](docs/acceptance/nor-198.md) before calling the deployment ready. Test current-checkout reservations through PR feedback and restart: competing sessions pause until explicit `resume` after release. Current-checkout cancellation ends the session after provider stop, preserves files/branch/PR, and requires a new delegation. Worktree cancellation remains resumable.

For user-systemd, adapt `systemd/linear-t3code-agent.service.template` to the installed paths and Node binary, copy it to your user unit directory, and enable it with your normal service-management process. Other supervisors can invoke `node dist/server.js` from the service directory with the same environment. No Pi executable or Pi SDK is required.

For upgrades: stop the bridge, take a consistent state/context backup, install/build the update, and restart against the same database. Do not reset the database or move worktrees to work around an integration error. The bridge reports authentication and contract failures; repair the adapter or credentials while preserving session identity. Only one process may own a database. A stale ownership record is recovered when its previous PID no longer exists; if that PID was reused by an unrelated process, stop and reconcile ownership manually rather than deleting the state database.

Routing and settings errors require correction followed by `resume`; duplicates never retry them. Established sessions keep their resolved project, settings and branch/worktree after later edits. There is no migration from the previous UUID-routing format. See [routing and permissions](README.md#routing-and-permissions) for workspace inheritance, reservation lifetime and cancellation behavior.
